## Navigation/context handoff

- `DestinationCard.tsx:247–266` serializes `carMode`, `publicModes`, party size, duration, and travel date into the destination link state.
- `DestinationDetails` resolves explicit navigation state before user preferences/defaults for mode eligibility, but its directions CTA ignores that resolved state and ignores the calculated result.
- `Compare` consumes `useOptionalTripContext()` for budget calculation, while its visible transport-time row still uses static `destination.transportOptions` and therefore does not preserve the active journey mode.
- `TripContext` remains the intended app-level owner; no second transport context is present or proposed.

## Directions builders found

Production source search for `google.com/maps`, `maps/dir`, `travelmode`, `directionsHref`, and route CTA builders found:

1. `src/features/destinations/DestinationDetails.tsx:468–475` — the only production Google Maps URL construction. Hard-coded `travelmode=transit`; endpoint is reconstructed from localized destination prose rather than the canonical Journey endpoint.
2. `src/features/destinations/components/DestinationAtAGlance.tsx:119–132,252–261` — presentational pass-through of `directionsHref`; it is not a second URL builder.

The tests contain one fixture URL in `DestinationAtAGlance.test.tsx`; it is not production behavior.

**Current production directions builders: 1.** The fix should retain one builder, move it behind the canonical Journey handoff seam, and have Detail pass the generated handoff rather than a free-form URL.

## Root-cause summary

1. **Mode mismatch:** Detail independently assumes transit after the canonical estimator has selected `my_car`/`car`.
2. **Endpoint mismatch:** Detail CTA reconstructs a destination label instead of consuming `Journey.destination`.
3. **Scope leak:** child cards inherit Detail/Home origin context; hub relationships are not converted into a local-access origin anchor before calculating the child card.
4. **Same-origin mismatch:** origin and destination are compared as near-equal coordinates only by the bounded estimator; no canonical anchor identity/“already there” contract exists in `JourneyService`.
5. **Partial representation gap:** ferry/local metadata can exist while the origin-aware estimator returns no complete route; the UI has no shared Journey state for “known local/access guidance, origin journey unavailable.”
6. **Compare drift:** active `TripContext` drives budget but the visible transport-time row uses static catalogue options.

## Intended post-fix ownership

- `JourneyService` remains the single traveller-facing journey resolver/owner and gains explicit scope, directionality, endpoint identity, and external-handoff capability.
- `JourneyBuilder` remains the adapter from existing estimate types; no `JourneyV3`, `TransportResult2`, or parallel context is introduced.
- `DestinationCard`, Detail, Home, Explore, and Compare consume the same resolver/semantic result for the journey they display.
- `DestinationAtAGlance` remains presentational and receives an optional handoff object; it never infers mode or endpoint.
- Planner remains an itinerary arranger unless a future ticket explicitly makes it journey-producing.
