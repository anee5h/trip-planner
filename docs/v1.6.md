# Architecture & Implementation Plan: v1.6.0 — Hierarchical Destination Relationships

Transform TabiMap's destination model from a flat collection of places into a relationship-based system where cities, towns, wards, attractions, parks, and landmarks remain first-class destinations while supporting rich parent-child navigation.

---

# Goals

## Primary Goals

- Introduce **Destination Relationships** without changing the existing destination architecture.
- Allow destination pages to recommend nearby and related destinations.
- Support future expansion to every major travel hub in Japan.
- Keep every destination independently searchable.
- Preserve existing Collections, Passport, and Planner functionality.

---

# Design Principles

## Everything is still a Destination

There is **no new entity** called "City."

Cities are simply another destination type.

```text
Destination

↓

City
Ward
Town
Village
Attraction
Temple
Shrine
Castle
Museum
Park
Island
Mountain
Beach
Lake
District
Shopping Area
```

---

## Relationships, Not Hierarchy

Avoid deeply nested structures.

Instead:

```text
Nagoya City

↓

Nagoya Castle

↓

Atsuta Shrine

↓

Osu Shopping Street
```

Each remains an independent destination.

---

## Parent Is Optional

Not every destination belongs to another.

Examples:

```text
Mount Fuji

parent

NULL
```

```text
Yakushima Island

parent

NULL
```

```text
Lake Biwa

parent

NULL
```

# Future Features Enabled

This architecture unlocks several features without changing the core model:

- **"Located In"** navigation on attraction pages.
- **Top Attractions** sections on city pages.
- **Nearby Destinations** recommendations.
- **Related Destinations** (e.g., Hakone ↔ Odawara ↔ Atami).
- Planner suggestions centered on cities.
- Statistics by destination type (cities visited, castles visited, temples visited, etc.).
- Better search and filtering (e.g., show only cities, only castles).

# Acceptance Criteria

## Data Model

- [ ] Introduce `DestinationType`.
- [ ] Add optional `parentId`.
- [ ] Add optional `relatedDestinationIds`.
- [ ] Preserve unique IDs for all destinations.

## Destination Pages

- [ ] City destinations display featured child destinations.
- [ ] Child destinations display their parent under "Located In."
- [ ] Existing destination pages remain functional without a parent.

## Naming

- [ ] All municipalities include their type (`City`, `Town`, `Village`) in display names.
- [ ] Existing destination slugs remain stable where possible to avoid broken links.

## Compatibility

- [ ] Collections continue referencing destination IDs only.
- [ ] Passport and Planner require no structural changes.
- [ ] Search indexes all destinations equally, regardless of type.

---

## Recommendation

I would **avoid introducing a separate "City" entity**. Keep the philosophy that **everything is a destination**. By modeling relationships instead of enforcing a strict hierarchy, you'll gain the flexibility to represent cities, wards, attractions, parks, islands, and natural landmarks consistently, while enabling much richer destination pages and future features with minimal architectural complexity.
